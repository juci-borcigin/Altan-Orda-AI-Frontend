## 2. スマホで Sample を見る（Preview 本命）

### 2.1 「`/sample` 以下だけ本番 Push」はできるか

**同一 Next.js 本番プロジェクトに対し、パス単位で一部だけデプロイする機能は Vercel にない。**

| やり方 | 可否 | 実態 |
|--------|------|------|
| 本番に `/sample` だけ載せる | △ | アプリ全体がビルド・デプロイされる。ルートを隠しても成果物は全ルート含む |
| Ignored Build Step で sample 変更時だけ本番ビルド | ○だが別物 | 「本番を汚す／汚さない」の制御であり、パス限定デプロイではない |
| **Preview デプロイ（専用ブランチ）** | ◎ | Mac 不要の URL。本番ドメインを触らない |
| `public/sample` 静的ホスト（Pages / Netlify Drop） | ◎ | 閲覧専用・最安。生成 API なし |
| Sample 専用の別 Vercel プロジェクト | ○ | Root を絞っても Next 構成次第では同じ `web` 全体ビルドになりがち。静的 export 向き |

**結論:** 「一部本番 Push」より **Preview（本命）＋必要なら静的ミラー** が正しい。

### 2.2 Preview 実装上の注意（問題になりうる点）

実装自体は可能。先に潰すべきは次。

1. **課金 API** — `/api/sample/**` の生成系は Preview でも鍵があれば叩ける。Preview では無効化、または秘密トークン必須にする。
2. **成果物サイズ** — `public/sample` の PNG（数十 MB〜）がデプロイを重くする。比較用は必要なラボだけ残すか、外部ストレージ参照を検討。
3. **認証** — 本番と同じ Google OAuth / Basic が Preview に掛かるとスマホ閲覧が詰まる。Sample 閲覧は許可メール or Sample のみ公開の方針を決める。
4. **環境変数** — 閲覧だけなら LLM 鍵は不要。生成を Preview で回すなら鍵と課金上限の明示が必要。
5. **本番ナビ汚染** — Preview ブランチを `main` にマージすると本番にも `/sample` が出る。恒久公開するか、ブランチ運用で分けるか決める。

**推奨オペレーション（案）**

1. `sample-lab` ブランチを切る（または PR の Preview URL を使う）。
2. 生成 API を Preview でガード。
3. スマホは `https://…vercel.app/sample` で閲覧。
4. Mac オフ・長期保管は `session1-visual-lab-offline.zip` / 静的ホストを併用。

### 2.3 Preview 運用（実装済み）

コード:

- `web/src/lib/course-maker/sample-api-guard.ts` — POST `/api/sample/**` ガード
- `web/src/auth.ts` — `AO_SAMPLE_PUBLIC=1` で `/sample` と GET `/api/sample/*` を公開

Vercel Preview 推奨 env:

```
AO_SAMPLE_PUBLIC=1
# 生成を Preview で回すときのみ:
# AO_SAMPLE_API_SECRET=<長い乱数>
# 生成を完全に閉じる:
AO_SAMPLE_API_DISABLED=1
```

手順:

1. `sample-lab` 等のブランチで PR を開き、Vercel Preview URL を取得する
2. Preview の Environment Variables に上記を設定する（Production とは分離）
3. スマホで `https://<preview>.vercel.app/sample` を開く
4. POST 生成は秘密ヘッダ `x-ao-sample-secret` なしでは拒否（Vercel 上は秘密未設定でも拒否）

## 3. ベース知識・信頼性 — 講座構成フェーズの再定義

### 3.1 提案フロー（殿下案）

```
1. モデルがコンテンツ・ドラフトを作成
2. 監査
   (1) 追加すべき最新情報を調査
   (2) コンテンツ・ドラフトのファクトチェック
3. コンテンツ・ドラフトを改訂・確定
4. 確定ドラフトをベースに、回数・時間から講座を構成
5. 回・セクションの本文出力
```

旧 Tier 1（講座構成）を **「知識ドラフト → 監査 → 確定 → 構成」** に拡張するイメージ。

### 3.2 方向性の妥当性

**妥当。推奨方向。**（2026-07-20 合意: ドラフト＝講座全体、監査＝要点＋上限付きで PoC 設計へ）

詳細スキーマ・上限・完了条件: `AO_Course_Foundation_PoC.md`

### 3.3 ツール／モデル割当（提案）

| ステップ | 提案 | 代替・メモ |
|----------|------|------------|
| **1 ドラフト** | **Luna** | 広く・安く草案。想像どおりでよい |
| **2 監査（調査＋FC）** | **Tavily（検索）+ Luna または Terra（判定）** | 下記 |
| **3 改訂・確定** | **Terra**（推奨） | 確定文は固く。軽量なら Luna でも可 |
| **4 講座構成** | **Terra** | 構造化・制約遵守向き。現状 outline と一致 |
| **5 回本文** | **Luna**（主）/ Terra フォールバック | テスト結論どおり |
| 画像 | Image 2 **Low** | テスト結論どおり |

#### ステップ2: Tavily vs Perplexity

| | Tavily | Perplexity Search API |
|--|--------|------------------------|
| 役割 | 生検索（ヒット URL・スニペット） | 検索＋要約寄りの結果 |
| AO との関係 | チャット経路で実績あり | **Tavily の将来比較・代替候補**（本文モデルとの比較対象ではない） |
| 講習監査での向き | **主候補**: クエリ制御・引用 URL が取りやすい | 監査の「調査」脚を短くしたいときの候補 |

**提案:** 当面 **Tavily を監査の調査脚**。判定・矛盾指摘・追記指示は **Terra（厳しめ）または Luna（安め）**。  
最初の PoC は「Tavily + Terra 判定」で確度優先、コストが見えたら判定を Luna に落とす。

Perplexity は「同じ監査ジョブを Tavily 経路と差し替えて品質・単価比較」用に残す（ユーザー規則どおり本文モデル比較には使わない）。

### 3.4 監査のパフォーマンス影響

殿下の見立て（**回・セクション本文には大きな影響がない**）は **概ね正しい**。

- 監査は **講座あたり数回（ドラフト確定まで）** で、ステップ5の N 回 × セクション生成とは直交する。
- 支配要因はステップ5＋画像。監査は相対的に小さい。

ただし監査を甘く見ない条件:

- ドラフトが超長文＋「全主張を個別検索」にすると、**検索回数 × LLM** で構成フェーズだけが高騰する。
- **上限を決める**: 例) 調査クエリ最大 N、監査 LLM 1〜2 呼び出し、対象は「数値・固有名・時事・論争点」のみ。

## 4. 出典（インライン参照）

- 「この部分の詳細はここを参照」を **セクション単位で確定**するのは、上記フローでも難しい。
  - 監査で URL は集まるが、ステップ5の本文がどの文に紐づくかの **対応付けが別問題**。
- 監査成果物として **講座レベルの参考リンク一覧** を残すのは比較的容易（Nice）。
- **結論:** インライン出典・「詳細はこちら」は **Nice to Have としてドロップ可**。必要になったら「講座末尾の参考リスト」から再開する。
